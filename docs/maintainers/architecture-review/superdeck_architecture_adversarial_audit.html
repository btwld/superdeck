SuperDeck architecture plan: adversarial audit

Decision: keep the main direction, but revise the execution plan before treating it as implementation-ready. The strongest work remains publication correctness, memory-loader completion, asset identity, and PDF lifecycle safety.

Repository: conceptadev/superdeck
Reviewed baseline: main@d160766c862a4ea7670a41c98f085bfae33a24f7
Status: source and plan audit; new application regressions were not executed.

Purpose. This is a correction addendum to the earlier architecture review, action plan, and backlog. It checks the plan against the deep-module guidance and repository conventions. It does not turn the 36 planning items into 36 confirmed defects.

What remains justified

Active-deck publication

The Wizard releases the saved deck before invoking the generated-result applier. Keep the publication finding and protect the saved-A/failed-B transition with a regression. The intended rule is to prepare the replacement completely, publish it only while it still owns the operation, and otherwise leave the previous deck coherent.

Memory loader

MemoryDeckLoader.reload() is empty while runtime reload enters loading state. Fix the contract mismatch directly. Add replay handoff tests so subscription cannot lose, duplicate, or reorder current state.

PDF lifecycle

Keep focused cleanup, cancellation, and stale-callback work. Narrow the architecture claim: the public PDF plugin interface is already small. A private capture-host extraction is conditional internal consolidation, not a required new application-facing abstraction.

Corrections to the plan

  1. Describe the method accurately. The earlier work was informed by improve-codebase-architecture and codebase-design, but did not execute the complete tool-driven sub-agent and grilling process. Behavioral verification remains pending.
  2. Do not make proposed modules mandatory. A new owner is justified only when it removes a proven caller obligation and concentrates a behavior rule.
  3. Remove soft scheduling dependencies. Publication handoff, refresh ownership, stale PDF callbacks, and writer serialization can be fixed independently unless implementation evidence shows a real prerequisite.
  4. Tighten acceptance tests. Observe publication during notifications, test replay during subscriber attachment, and test old-asset lifetime while replacement cleanup runs.
  5. Use scope-sensitive merge gates. Checks required by changed behavior must pass, or the maintainer must explicitly accept a documented limited exception. Existing green CI is baseline evidence only.
  6. Separate fixes, structural proposals, and product decisions. Do not treat one backlog as one mandatory refactor program.

Final disposition

The architecture direction survives the adversarial review. Blanket approval of the original 36-item execution plan does not. Require executed evidence for each behavior an implementation claims and prefer the smallest change that removes a proven caller obligation.
